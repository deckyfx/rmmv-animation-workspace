## Project Overview

RMMV Animation Studio is a **Bun workspace monorepo** containing two packages:

1. **@decky.fx/rmmv-animation-player**: Standalone NPM package for playing RMMV animations in any Phaser 3 project
2. **@decky.fx/rmmv-animation-studio**: Web application for reading, playing, and editing RPG Maker MV animation files

The monorepo structure allows the Studio to use the Player package as a workspace dependency while keeping the Player package independently publishable to NPM.

## Technology Stack

- **Runtime**: Bun server (serving React app)
- **Monorepo**: Bun Workspaces
- **Frontend**: React + TypeScript
- **State Management**: Zustand (for React ↔ Phaser communication)
- **Database**: SQLite with Drizzle ORM
- **Game Engine**: Phaser 3 (16:9 aspect ratio, embedded in React)
- **Language**: TypeScript (strict typing, no `any` or `unknown`)
- **Architecture**: Class-based OOP with TSDoc documentation
- **Communication**: EventBus pattern via Zustand store

## RMMV Animation Format

The `Animations.json` file from RPG Maker MV contains animation definitions with:
- **animation1Name/animation2Name**: Sprite sheet filenames (without extension)
- **frames**: Array of frame data with cell configurations `[cellId, x, y, scale, rotation, flip, opacity, blendMode]`
- **timings**: Sound effects, screen flashes, and other timing events
- **position**: Animation positioning (0=head, 1=center, 2=feet, 3=screen)

Animation sprites are located in `assets/img/animations/` as PNG files.

### Cell Indexing (Critical for Renderer)

**IMPORTANT**: cellId uses **row-major indexing**:

```
Formula: cellId = (row * columns) + column

Example with 5 columns:
┌────┬────┬────┬────┬────┐
│ 0  │ 1  │ 2  │ 3  │ 4  │  Row 0
├────┼────┼────┼────┼────┤
│ 5  │ 6  │ 7  │ 8  │ 9  │  Row 1
├────┼────┼────┼────┼────┤
│ 10 │ 11 │ 12 │ 13 │ 14 │  Row 2
└────┴────┴────┴────┴────┘

cellId 6 = row 1, col 1 → x: 192px, y: 192px
```

**Key Facts**:
- Cell size: Always 192×192 pixels (use `RMMV_CELL_SIZE` constant)
- Column count: Varies per sprite sheet (3-5 columns typically)
- Row count: Variable (depends on sprite sheet content)
- Real RMMV data shows cellIds up to 112+ for larger sheets
- Use `getCellCoordinates(cellId, columns)` utility to calculate slice position

**Cell Size Constant**:
```typescript
import { RMMV_CELL_SIZE } from '@decky.fx/rmmv-animation-player';

// Use this constant instead of hard-coding 192
const columns = imageWidth / RMMV_CELL_SIZE;
const x = col * RMMV_CELL_SIZE;
const y = row * RMMV_CELL_SIZE;
```

**Calculating Cell Position**:
```typescript
import { getCellCoordinates, RMMV_CELL_SIZE } from '@decky.fx/rmmv-animation-player';

// For a 5-column sprite sheet
const coords = getCellCoordinates(cellId, 5);
// Returns: { row, col, x, y }

// Renderer slices sprite sheet at (x, y) with size RMMV_CELL_SIZE × RMMV_CELL_SIZE
```

### Validation Rules (Verified Against Real Data)

Based on testing against 120 real RMMV animations:

1. **cellId**: -1 (empty) or non-negative integer (no upper limit)
2. **rotation**: -360 to 360 degrees (negative = counter-clockwise)
3. **scale**: Any positive number (typically 50-300)
4. **flip**: 0 or 1 only
5. **opacity**: 0-255
6. **blendMode**: 0 (Normal), 1 (Additive), 2 (Multiply), 3 (Screen)
7. **SE pitch**: 10-200+ (editor shows 50-150, but real data extends range)

## Architecture Guidelines

### Application Architecture

The Studio follows a React + Phaser hybrid architecture mimicking RPG Maker MV's Animation Editor:

**UI Layout (3-Panel Design)**:
- **Left Panel**: Animation list (browsable list of all animations)
- **Middle Panel**: Phaser Scene (16:9 aspect ratio for preview/playback)
- **Right Panel**: Toolbox with three sections:
  - General Settings (name, two sprite sheet selectors)
  - SE and Flash Timing (sound effects and screen flash configuration)
  - Frames (frame-by-frame animation editor)

**Communication Architecture**:
```
React UI (HTML/CSS) ←→ Zustand Store (EventBus) ←→ Phaser Scene
     │                        │                         │
  User Input            State Management          Animation Rendering
```

- **React**: Handles all UI controls and user interaction
- **Zustand Store**: Acts as EventBus for bidirectional communication
- **Phaser Scene**: Renders animations, responds to state changes

**Asset Loading Strategy**:
- **Lazy Loading**: Load assets on-demand, not all at once
- **Asset Manager**: Track loaded/unloaded assets per animation
- **Unload Unused**: Clear unused assets when switching animations
- **Sprite Sheet Caching**: Keep recently used sheets in memory with LRU cache

### Player Package Design

The Player package is designed for:
1. **Framework Agnostic Core**: Separate parsing logic from Phaser rendering
2. **Phaser Integration Layer**: Clean adapter for Phaser Scene integration
3. **Configuration Export**: Generate portable JSON that other projects can consume
4. **Type-Safe**: Full TypeScript definitions for all data structures

### Key Classes

```typescript
// Player Package (@decky.fx/rmmv-animation-player)
class AnimationParser {
  // Parse and validate Animations.json
  static parse(data: unknown): RMMVAnimationsData
  static validate(data: unknown): ValidationResult
  static getAnimationById(data: RMMVAnimationsData, id: number): RMMVAnimation | null
}

class AnimationPlayer {
  // Play RMMV animations in Phaser Scene
  constructor(scene: Phaser.Scene, config: AnimationConfig)
  async preload(): Promise<void>
  play(target: TargetPosition, options?: PlaybackOptions): void
  stop(): void
  pause(): void
  resume(): void
}

class AssetLoader {
  // Preload sprite sheets and sound effects
  async loadAnimationAssets(animation: RMMVAnimation): Promise<PreloadedAsset[]>
  getCachedAsset(filename: string): PreloadedAsset | undefined
  clearCache(): void
}
```

### Data Flow

```
User Interaction (React UI)
         ↓
   Zustand Store (EventBus)
         ↓
Animations.json → AnimationParser → RMMVAnimation
                                         ↓
                          AnimationPlayer (Phaser Scene)
                                         ↓
                          AnimationConfig → JSON Export
```

**Event Flow Examples**:
- User selects animation → Zustand updates → Phaser loads/plays animation
- User edits frame → Zustand updates → Phaser re-renders preview
- Animation complete → Phaser emits event → Zustand updates UI state

## Development Standards

### TypeScript

- Use strict mode with no `any` or `unknown` types
- Document all classes, methods, and public APIs with TSDoc
- Define interfaces for RMMV data structures
- Export types for external consumption

### Code Style

- Class-based OOP architecture
- Single Responsibility Principle
- Prefer composition over inheritance
- Performance-optimized (minimize allocations in animation loops)

### Asset Loading

**CRITICAL**: With 100+ sprite sheets, load assets lazily:

- **On-Demand Loading**: Load only sprites for the selected animation
- **Asset Tracking**: Maintain loaded asset registry in Zustand store
- **LRU Cache**: Keep recently used assets (configurable limit, e.g., 10 sheets)
- **Unload Strategy**: Clear unused assets when switching animations
- **Preloading**: Optional preload adjacent animations in list
- **Loading States**: Show loading indicators during asset fetching
- **Error Handling**: Gracefully handle missing sprite sheets
- **Dynamic Paths**: Support configurable asset base paths for SDK portability

### Testing Approach

- Test parser with actual RMMV Animations.json files
- Validate output configuration JSON
- Visual testing for animation playback accuracy
- Performance benchmarks for animation rendering

## Critical Design Considerations

### Performance

- Animations run at 60 FPS: optimize render loop
- Pre-process sprite sheet data for fast lookup
- Use object pooling for frequently created objects
- Cache parsed animation data

### Portability (Player Package)

The Player package must work in other Phaser projects:
- Minimize dependencies (only `phaser` as peer dependency)
- Clear API documentation
- Example usage code
- Configuration schema validation
- No Studio-specific dependencies

### Fidelity

Animations must match RMMV behavior exactly:
- Respect blend modes and opacity
- Accurate timing with frame rates
- Proper coordinate system conversion (RMMV → Phaser)
- Sound effect synchronization

### Monorepo Best Practices

- **Build Order**: Player must be built before Studio type-checks
- **Import Paths**: Studio uses package name, Player uses relative paths
- **Type Declarations**: Player generates `.d.ts` files for Studio consumption
- **Independent Publishing**: Player can be published to NPM independently
